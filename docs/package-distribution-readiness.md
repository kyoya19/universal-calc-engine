# Package distribution readiness

## Purpose

The analytical core already has a functional-contract v1 boundary. This document defines the separate package/build and dependency-lock boundary used to hand the repository to a third party that needs a consumable JavaScript library artifact.

This work does **not** publish the package to an npm registry and does not declare a semantic-version `1.0.0` release.

## Package status

The root package remains:

```text
name: universal-calc-engine
version: 0.0.1
private: true
type: module
```

`private: true` intentionally remains in place. Registry publication is outside this boundary.

The existing commercial-use terms remain in `COMMERCIAL-LICENSE.md`. The packed artifact includes that file and the root `README.md`; no license text is rewritten by the build.

## Production entrypoint

The source public surface remains:

```text
packages/core/src/index.ts
```

The production build emits:

```text
dist/index.js
dist/index.d.ts
```

and the root package metadata points `main`, `module`, `types`, and the root `exports` entry at those files.

The package is ESM-only at this boundary. No CommonJS build is claimed.

## Build configuration

Production build configuration is isolated in:

```text
tsconfig.build.json
```

It includes only:

```text
packages/core/src/**/*.ts
```

so source tests, examples, and Vitest configuration are not emitted into `dist/`.

The existing development `tsconfig.json`, `npm run typecheck`, and source-based Vitest tests remain unchanged.

## Node ESM module-specifier boundary

The source tree uses TypeScript/Bundler-style relative specifiers such as:

```text
./model
```

A plain TypeScript ESM emit preserves those extensionless specifiers, while Node ESM consumers require executable relative specifiers such as:

```text
./model.js
```

The build therefore performs two explicit steps:

```text
TypeScript production emit
→ rewrite relative emitted JS/declaration specifiers to .js
```

Only generated files in `dist/` are rewritten. Source imports are not mass-edited.

The same `.js` specifier boundary is applied to generated declaration files so a NodeNext TypeScript consumer can resolve the declarations consistently with the runtime ESM graph.

## Dependency lock and reproducible install

The repository now commits an npm-generated:

```text
package-lock.json
```

with:

```text
lockfileVersion: 3
```

The lockfile was generated by npm tooling from the existing `package.json`; it was not hand-authored. The package version and declared dependency ranges were not changed while introducing the lock.

CI installs the committed graph with:

```text
npm ci --no-audit --no-fund
```

rather than resolving a fresh graph through `npm install`.

This provides deterministic npm dependency resolution for the committed lockfile. It does not claim bit-for-bit reproducibility of platform-specific optional package installation or npm's external registry service itself.

The lockfile is a repository/development input. It is explicitly rejected by the package smoke test if it appears in the published tarball payload.

## Current dependency boundary

The root package currently has no `dependencies` field and therefore no declared runtime dependency packages. Its direct dependencies are development-only:

```text
@types/node
TypeScript
Vitest
```

The npm-generated lockfile currently resolves the key direct versions to:

```text
@types/node: 20.19.43
TypeScript: 5.9.3
Vitest: 1.6.1
```

The packed library consumer smoke test installs only the packed `universal-calc-engine` artifact and successfully imports the runtime API, which also verifies that the emitted production graph does not rely on undeclared external runtime packages.

## Security audit boundary

The dependency audit performed when the lockfile was introduced reported four advisories in the complete development dependency graph:

```text
critical: 1
high: 1
moderate: 2
```

All four are development-only and originate from the Vitest toolchain:

```text
vitest 1.6.1
├─ vite 5.4.21
│  └─ esbuild 0.21.5
└─ vite-node 1.6.1
```

The advisories are:

- `vitest`: critical; the affected behavior concerns the Vitest UI server. The repository runs `vitest run` and does not start the Vitest UI server in CI.
- `vite`: aggregate high severity through development-server/path-handling advisories. The library build does not run or expose a Vite development server; one of the included advisories is specifically about Windows path handling while CI currently runs on Ubuntu.
- `vite-node`: moderate through its affected Vite dependency.
- `esbuild`: moderate; the affected behavior concerns the esbuild development server. This repository does not start that server.

A production-only audit returns zero vulnerabilities:

```text
npm audit --omit=dev
→ 0 vulnerabilities
```

CI therefore uses a production dependency security gate:

```text
npm run audit:production
```

which executes:

```text
npm audit --omit=dev --audit-level=moderate
```

Development advisories are recorded but are not converted into a permanent CI failure while the current remediation offered by npm requires a semver-major Vitest upgrade.

At the time of this boundary, npm reports the automatic remediation as:

```text
vitest 4.1.10
semVerMajor: true
```

No `npm audit fix --force` is applied. Upgrading Vitest across major versions is a separate compatibility increment that must rerun the complete test/build/package boundary before adoption.

## Commands

Development checks:

```text
npm run typecheck
npm test
```

Production dependency security check:

```text
npm run audit:production
```

Production artifact build:

```text
npm run build
```

Packed consumer verification, after a successful build:

```text
npm run package:check
```

CI runs the boundaries in order:

```text
npm ci
→ production dependency audit
→ typecheck
→ test
→ build
→ package smoke test
```

## Package smoke test

`npm run package:check` performs an actual package boundary check rather than importing source files directly.

It:

1. verifies `dist/index.js` and `dist/index.d.ts`,
2. runs `npm pack --json`,
3. checks the tarball file list,
4. rejects source/tests/examples/scripts/build configuration and `package-lock.json` leaking into the packed package,
5. installs the generated tarball into a temporary consumer project with install scripts disabled,
6. imports the installed package with Node ESM,
7. verifies representative forward, direct, dispatcher, reverse, and handoff runtime exports,
8. compiles a separate TypeScript consumer with `moduleResolution: NodeNext`, and
9. removes the temporary consumer and tarball.

Representative public runtime exports checked include:

```text
evaluateDefinitionModel
evaluateAcyclicDirectDefinitionModel
evaluateDefinitionModelWithSolver
estimateExternalReverseInput
toForwardResultHandoff
toReverseResultHandoff
```

This is intentionally a representative public-surface smoke test, not one micro-test per export.

## Packed files

The package `files` boundary is limited to:

```text
dist
README.md
COMMERCIAL-LICENSE.md
```

`package.json` is included by npm packaging semantics.

Tests, examples, `.github`, scripts, TypeScript configs, Vitest config, and the repository lockfile are not intended package payload.

## Existing contracts unchanged

This distribution and supply-chain work does not change:

```text

ForwardEvaluationOptions
ForwardEvaluationResult
ForwardResultHandoff schemaVersion: 1
reverse estimator semantics
ReverseResultHandoff
FiniteDecisionProcess P0
```
